# Edge cases: internal classification, deterministic export

## The problem

`templates/sit-script-template.xlsx` restricts the **Case Type** column to a
two-value dropdown:

```
D2:D20  dataValidation list -> "Positive,Negative"
```

There is no `Edge`. The office template is not modified in V1, so nothing may
write `Edge` into that column — a workbook whose own dropdown rejects its
contents is a defect, not a feature.

QATOOL still needs the classification. Edge coverage is a real SIT concern, and
collapsing it into Positive/Negative at generation time would destroy the
distinction permanently.

## The rule

`Edge` is a first-class value **in the canonical model only**. Export projects
it down; the canonical model never loses it.

| Internal `case_type` | `edge_polarity` | Exported Case Type | Exported Expected Result  |
| -------------------- | --------------- | ------------------ | ------------------------- |
| `Positive`           | `null`          | `Positive`         | unchanged                 |
| `Negative`           | `null`          | `Negative`         | unchanged                 |
| `Edge`               | `valid`         | `Positive`         | `[Edge Case] ` + original |
| `Edge`               | `invalid`       | `Negative`         | `[Edge Case] ` + original |

### Why `edge_polarity` exists

The mapping has to be deterministic and rule-based — never an LLM call at
export time. But "valid boundary" versus "invalid boundary" is a semantic
judgement, and nothing in `expected_result` reliably encodes it. Inferring it at
export would mean either keyword heuristics (quietly wrong) or a model call
(forbidden).

So the judgement is recorded **on the row**, at the moment the test case is
created:

- the LLM proposes it during generation (milestone 4);
- validation and the Results page flag any that are missing;
- export only reads it (built; `server/export/edge-case-mapping.js`).

Export therefore reduces to a pure lookup over stored data.

### Why there is no default

`edge_polarity` is **required** when `case_type` is `Edge`, and **rejected**
otherwise. It has no fallback value.

A default would mean an `Edge` case with a missing polarity gets exported as
something — and whichever value were chosen, some boundary-rejection test would
eventually ship labelled as a success path, with nobody looking. Instead the
missing value is a hard validation error that reaches QA.

The invariant is enforced at every layer it could be violated:

| Layer      | Where                                                    |
| ---------- | -------------------------------------------------------- |
| Validation | `server/schema/testcase.js` (`applyEdgePolarityRule`)    |
| Results UI | `web/src/stages/ResultsStage.jsx` (flagged as blocking)  |
| Export     | `server/export/edge-case-mapping.js` (`checkExportable`) |

A fourth check runs on the generated bytes: the exporter reads its own workbook
back and asserts every Case Type landed inside the template's dropdown.

There is no storage layer to enforce it in - QATOOL V1 keeps the canonical
project in browser memory for one session and persists nothing.

### A missing polarity blocks the export

QATOOL does not edit generated content, so an `Edge` case that arrives without a
polarity cannot be fixed in place — it has to be regenerated. Validation reports
it, the Results page flags it as blocking, and export refuses with
`EXPORT_BLOCKED` rather than guessing a direction.

## The `[Edge Case] ` prefix

The exported Expected Result is prefixed so the Edge nature survives in the
workbook, which has nowhere else to carry it:

```
internal   expected_result = "Transaction is accepted at the maximum allowed amount."
exported   Expected Result = "[Edge Case] Transaction is accepted at the maximum allowed amount."
```

Three constraints on the prefix:

1. **Export-only.** It is never written back to the canonical model. Otherwise a
   generate → export → edit → re-export cycle accumulates prefixes.
2. **Idempotent.** If the stored text already begins with the marker — a
   reviewer may have typed it by hand — it is not prepended again.
3. **English, always.** Expected Results are frequently written in Indonesian.
   The marker is a machine-readable tag, so it stays consistent rather than
   matching the surrounding prose.

The Expected Result column carries no data validation in the template, so
prefixing cannot invalidate a cell.

## Scope

The exported workbook is a lossy projection of the canonical model, never the
reverse. `Edge` joins the list of things the spreadsheet cannot carry, alongside
`requirement_ids`, `source_references`, `confidence` and `warnings`.

If the office template's dropdown is ever widened to include `Edge`, only
`server/export/edge-case-mapping.js` and the template asset need to change.
Nothing upstream is aware of the downgrade.

## Verification

`server/export/fixtures/sample-test-cases.js` covers every branch — Positive,
Negative, Edge/valid, Edge/invalid, a pre-marked Edge case and text containing
`&`, `<` and `"`. `server/export/sit-script-export.test.js` asserts the produced
workbook against them, and the output has also been opened independently with
Python's openpyxl (warnings promoted to errors) at 0, 6 and 120 rows.
